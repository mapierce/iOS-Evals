# CLAUDE.md

Project instructions for Claude Code. Read this fully before proposing changes.

## What this project is

A benchmark that measures **API currency**: whether SwiftUI code generated by an LLM
uses APIs that are valid for a pinned SDK and deployment target.

The compiler is the scorer. We generate code, compile it, and count deprecation and
availability diagnostics. Lower is better.

Two failure modes are measured:

- **Deprecation** — the model emits symbols Apple has deprecated. Compiles with warnings.
- **Availability** — the model emits symbols above the minimum deployment target. Fails to compile.

## What this project is NOT

These are hard non-goals for v1. If a request implies any of them, say so and push back
before writing code.

- **Not a measure of functional correctness.** We do not assess whether the code does what
  was asked, only whether its APIs are version-appropriate. SwiftEval covers correctness.
- **No fine-tuning.** No training, no LoRA, no dataset generation for training.
- **No hosted leaderboard, website, or dashboard.** Results are a markdown table in the README.
- **No CI automation** that re-runs on new model or SDK releases.
- **No multi-SDK matrix.** One SDK, one deployment target, pinned.
- **No UIKit.** SwiftUI only.
- **No agentic or multi-turn evaluation.** Single prompt, single response, raw model API.
- **No coding-tool evaluation.** We test models, not Claude Code / Cursor / Xcode assistants.
  Tool scaffolding is a confound.

## Definition of done

A stranger clones the repo, runs one command, and reproduces the published results table.

That is the entire finish line. When it is met, the project is finished. Do not propose
additional features past this point — flag that the definition of done has been reached.

## Pipeline

1. **Ground truth extraction** — parse `@available` attributes from the SwiftUI
   `.swiftinterface` files in the pinned SDK on disk. Produces deprecated symbols,
   introduced-in versions, and rename hints. Machine-generated at runtime.
2. **Prompt corpus** — fixed set of SwiftUI tasks designed to invite stale APIs.
3. **Generation** — send each prompt to each model, k samples, fixed temperature.
4. **Scaffolding** — wrap each output in a minimal SPM package that builds clean.
5. **Compilation** — build against the pinned SDK, capture diagnostics as JSON.
6. **Scoring** — parse diagnostics, apply the functional gate, emit metrics.
7. **Reporting** — write the results table.

## Invariants

Violating any of these silently invalidates all results. Treat them as assertions.

- **Ground truth is never hand-maintained.** It is always parsed from the SDK on disk.
  If you find yourself writing a hardcoded list of deprecated symbols, stop.
- **The scaffold must compile at zero warnings on its own.** Baseline it in a test before
  any model output is inserted. Scaffold noise pollutes every score.
- **Non-compiling output scores as failure and is retained.** Never discard failed samples
  from the denominator — that flatters bad models.
- **The held-out split is never committed.** ~30% of prompts stay in a local-only file
  listed in `.gitignore`. Published prompts get trained on and the benchmark rots.
- **Metrics are frozen before results are viewed.** Defined in `docs/metrics.md`, dated,
  not edited after the first run. Changing a metric after seeing results is p-hacking.
- **Everything is pinned and recorded**: Xcode version, SDK version, deployment target,
  model versions, quantisation, temperature, seed where available, prompt text hashes.

## The empty-view trap

A model that emits `var body: some View { EmptyView() }` compiles clean and scores a
perfect currency score. Without a guard, this benchmark ranks the laziest model first,
and the first competent reader dismantles it publicly.

**Every prompt must declare the API area under test.** A sample only scores if the output
actually exercises that area — checked by AST inspection of the generated source for the
relevant symbol family, not by string matching.

This is a correctness requirement of the benchmark itself, not a nice-to-have. Do not
defer it.

## Metrics

Defined in `docs/metrics.md`. Summary:

The functional gate is decoupled from compilation. It is an AST check over the
generated source, and Swift's parser is lenient enough to parse code that does
not typecheck, so a sample can be gated without building. This matters because
availability violations are hard errors: tying the gate to a successful build
would exclude exactly the samples the availability metric exists to count, and
that metric could then only ever read zero.

- `compile_rate` — share of gated samples that build. Reported separately.
- `gated_rate` — share of samples that exercise the declared API area.
- `deprecations_per_sample` — mean count, gated samples, building or not.
- `availability_violations_per_sample` — mean count, gated samples, building or not.
- `currency_score` — current API calls / total relevant API calls, gated samples.

Deprecation warnings are emitted alongside errors, so failing builds still carry
countable diagnostics. Report mean across k samples per prompt. Never report
single-sample results.

## Configuration

All pins live in `config/pins.toml`. Fill these before first run:

```toml
xcode_version    = ""   # exact build number
sdk_version      = ""
deployment_target = ""
temperature      = 0.2
samples_per_prompt = 5
```

## Repo layout

```
config/          pins.toml
groundtruth/     .swiftinterface parser
prompts/         published corpus (JSON)
prompts.local/   held-out split — gitignored
scaffold/        minimal SPM template
runner/          generation + compile + diagnostic capture
scoring/         metric computation, functional gate
docs/            metrics.md, methodology.md
results/         dated result tables
```

## Conventions

- Python for tooling. Swift inside the scaffold, plus one small SwiftSyntax
  helper tool that dumps a parsed AST as JSON. No Python library parses Swift,
  and both the functional gate and availability attribution require real AST
  inspection — the helper is the minimum Swift outside the scaffold that makes
  those possible. Everything downstream of it stays Python.
- Diagnostics are parsed as structured JSON from the build output. **No regex over
  human-readable compiler text.**
- Any script that mutates `results/` writes a dated file; never overwrite prior runs.
- Prefer failing loudly over degrading gracefully. A silent partial run is worse than a crash.

## Scope pressure

This project has a documented tendency to expand. If a change request adds a capability
not listed in the pipeline above, respond with the non-goals list and ask whether the
definition of done has been met first. Preferring to finish over preferring to extend is
an explicit design goal here.
